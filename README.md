# Автотести фільтра «Ціна» — makeup.com.ua

Playwright + TypeScript. Покривають фільтр ціни (на сайті блок називається «Вартість») на сторінці категорії [Парфумерія](https://makeup.com.ua/ua/categorys/3/) для десктопної та мобільної версії.

## Запуск

Потрібен Node.js 20 або новіший.

```bash
npm ci
npx playwright install chromium
npm test
```

| Команда | Що робить |
| --- | --- |
| `npm test` | усі тести, десктоп і мобільна версія |
| `npm run test:desktop` | лише десктоп (Desktop Chrome, 1440×900) |
| `npm run test:mobile` | лише мобільна версія (емуляція Pixel 7) |
| `npm run test:headed` | із видимим браузером |
| `npm run report` | HTML-звіт останнього запуску |
| `npm run typecheck` | перевірка типів TypeScript |

## Структура

```
playwright.config.ts              налаштування, проєкти desktop і mobile
src/
  pages/category.page.ts          сторінка категорії, синхронізація з API
  pages/price-filter.component.ts фільтр; ховає різницю між десктопом і мобільною версією
  fixtures.ts                     готова сторінка для тесту, приховування оверлеїв
  assertions.ts                   спільні перевірки стану фільтра
  utils/price.ts                  розбір цін, побудова діапазонів
tests/
  presets.spec.ts                 кнопки-діапазони
  manual-input.spec.ts            поля «Від» і «До», межі, некоректні значення, порожній результат
  reset.spec.ts                   скидання фільтра
  url-state.spec.ts               перезавантаження, посилання, пагінація
  layout.spec.ts                  особливості десктопної та мобільної версії
  known-issues.spec.ts            знайдений дефект
```

Один і той самий тест виконується в обох проєктах: десктопна бічна панель і мобільна панель сховані всередині `PriceFilter`. Тести лише для однієї версії лежать у `layout.spec.ts`.

## Як забезпечена стабільність

**Незалежність від товарів і цін.** У тестах немає жодної конкретної ціни чи назви товару:
- діапазони обчислюються з цін, які є на сторінці зараз (`rangeFromPrices`, `median`);
- пресети читаються з інтерфейсу, тому зміна їхнього набору не ламає тести;
- перевіряються інваріанти, а не числа: «товарів стало менше», «ціни в межах діапазону».

**Без `sleep`.** Сервер спершу віддає HTML без фільтра, а потім клієнт сам запитує товари. Якщо перевіряти одразу, тест прочитає старі картки. Тому `syncWithProducts` виконує дію, чекає відповідь API `/shop/v1/categories/3/products/` саме з потрібними `priceFrom` і `priceTo`, а далі чекає, поки інтерфейс покаже цю відповідь. Параметри важливі: одразу після завантаження сайт може надіслати ще й зайвий запит без фільтра.

**Готовність сторінки.** Сторінка спершу приходить готовим HTML, і лише потім React підключає до неї обробники (гідратація). Клік до цього моменту губиться. Але й після гідратації застосунок ще близько секунди ініціалізується: зміна фільтра в цей час дає зайвий запит без фільтра й очищене поле, а зрідка фільтр губиться зовсім (див. проблему 4). Тому `open()` чекає дві речі: гідратацію і перший момент, коли браузер звільнився від стартової роботи (`requestIdleCallback`). Це не пауза, бо очікування підлаштовується під швидкість машини.

**Зсув макета.** Коли тест прокручує сторінку до пагінації, сайт догружає блоки під нею (відгуки, «Знайди майстра або салон»). Браузер утримує позицію екрана, і пагінація «підстрибує» вгору саме під час кліку: кнопка миші натискається на «2», а відпускається вже на іншому елементі, тому подія `click` не виникає (приблизно 1 запуск із 6). Тому `goToPage` спершу прокручує до кнопки, чекає, поки сторінка завершить запити до API, і лише потім клікає.

**Живі дані.** Кількість товарів змінюється просто під час тесту (4982 → 4983 за кілька секунд), тому значення лічильника з різних запитів порівнюються з допуском 1 % (`expectSameTotal`).

**Лише справжні результати.** У сітку вбудовані банери та слайдери з відгуками. Перевіряються тільки прямі нащадки сітки, картки-товари. Товари не в наявності не мають ціни й пропускаються.

**Допуск на аномалії даних.** На сторінці дозволено до двох карток із ціною поза діапазоном (див. дефект 2). Зламаний фільтр дасть набагато більше таких карток і тест упаде, а кожна знайдена аномалія потрапляє в звіт як анотація `price-outlier`.

**Локатори.** На сайті немає `data-testid`, а назви класів закінчуються хешем збірки, тому використовуються ролі та тексти кнопок і стабільний префікс класу (`[class*="PriceSelector__priceButton"]`).

**Сайт живий і під захистом.** Перед сайтом стоїть AWS WAF. Звичайний браузер проходить його перевірку сам, обходу захисту в проєкті немає. Щоб не навантажувати продакшн, працює 2 воркери. З IP дата-центрів, зокрема CI-раннерів, WAF може блокувати запити.

**Оверлеї.** Банер cookie та підказка MAKEUP Rewards перекривають елементи керування, тому приховані через CSS. Згода на cookie не надається.

## Знайдені проблеми

Спостерігалося 07–08.11.2026 у категорії «Парфумерія».

### 1. Значення поля «До» стирається під час введення

1. Ввести значення в поле «Від».
2. Натиснути Tab і відразу ввести значення в поле «До».

**Очікувано:** застосовуються обидві межі.
**Фактично:** після оновлення списку поле «До» стає порожнім, застосовується лише «Від».

Покрито тестом у `known-issues.spec.ts` з позначкою `test.fail()`. Коли дефект виправлять, тест стане червоним: це сигнал прибрати позначку.

### 2. Картка з ціною поза діапазоном

Banderas King of Seduction (ціна на картці 980 ₴) потрапляє у фільтр 618–700 ₴, але не потрапляє у 975–985 ₴. Жоден об'єм цього товару не коштує 600–700 ₴ (803–1156 ₴), і вирахування знижки 363 ₴ теж не пояснює результат. Схоже на розбіжність між ціною у фільтрі й ціною на картці, причину варто уточнити у розробників.

### 3. «Від» більше за «До»

`Від 500, До 100` не дає помилки чи порожнього списку. Показуються товари рівно за 500 ₴, а чіп містить текст «від 500 до 100». Очікувана поведінка не описана, тому тест перевіряє лише мінімум: сторінка працює і товарів не більше, ніж для самого «Від».

### 4. Введення одразу після завантаження сторінки

1. Відкрити категорію.
2. Протягом приблизно секунди після того, як сторінка стала інтерактивною, ввести значення у «Від» і перевести фокус.

**Очікувано:** застосовується фільтр «від N».
**Фактично:** сайт спершу надсилає зайвий запит без фільтра, і поле на мить стає порожнім, а потім фільтр застосовується. Але зрідка, приблизно раз на 40 тестів, фільтр губиться повністю: поле порожнє, список не відфільтрований.

Автотести перед діями чекають завершення ініціалізації (див. «Готовність сторінки»), бо перевіряють сам фільтр, а не реакцію сторінки в першу секунду. Окремого тесту на це немає: збій рідкісний, і такий тест сам був би нестабільним.

### 5. Дрібні зауваження

- Enter у полі не застосовує фільтр, значення застосовується лише після втрати фокусу.
- `12.5` у полі перетворюється на `125`: крапка відкидається, і значення мовчки стає в 10 разів більшим.
- Обраний пресет ніяк не виділений.
- Для порожнього результату немає повідомлення, лише «0 товарів».

## Що не покрито

Поєднання з іншими фільтрами та сортуванням, інші категорії, браузери Firefox і WebKit. Це наступні кроки, якщо набір розвиватиметься.
